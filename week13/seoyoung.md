## 문제 1

### 문제 정보

* 문제명: 주차 요금 계산
* 문제 링크: https://school.programmers.co.kr/learn/courses/30/lessons/92341
* 사용한 알고리즘 / 자료구조: 구현, 해시(딕셔너리), 문자열 파싱

### 처음 접근 방식

입차와 출차가 짝을 이루니 `IN` 기록을 만나면 저장해두고 `OUT`을 만나면 그 자리에서 요금을 계산해 더하면 된다고 생각했다. 그렇게 짰더니 테스트케이스 대부분이 틀렸다. 같은 차가 여러 번 들어오고 나가는 경우에 매번 기본 요금이 다시 붙어서, 짧게 여러 번 주차한 차의 요금이 터무니없이 커졌다. 문제를 다시 읽어보니 요금은 "누적 주차 시간"에 한 번만 매기는 거였다. 그리고 출차 기록이 아예 없는 차량 처리를 빼먹어서, 들어왔다가 안 나간 차가 요금 목록에 등장하지 않았다.

### 풀이 방법

1. 차량별 입차 시각을 담을 `in_time` 딕셔너리와 누적 주차 분을 담을 `total` 딕셔너리를 만든다.
2. `records`를 순서대로 읽어 `시각 / 차량번호 / 구분`으로 쪼개고, 시각은 `시 * 60 + 분`으로 바꿔 분 단위 정수로 통일한다.
3. `IN`이면 `in_time[차량번호]`에 시각을 넣는다. `OUT`이면 `total[차량번호]`에 `출차 시각 - 입차 시각`을 더하고 `in_time`에서 그 차량을 지운다.
4. 기록을 다 돌고 나서 `in_time`에 남아 있는 차량은 출차하지 않은 차량이므로, `23:59`(1439분)에 나간 것으로 보고 같은 방식으로 누적 시간을 더한다.
5. 누적 시간이 기본 시간 이하면 기본 요금, 초과하면 `기본 요금 + ceil((누적 시간 - 기본 시간) / 단위 시간) * 단위 요금`으로 계산한다.
6. 차량번호를 오름차순으로 정렬해 그 순서대로 요금 리스트를 반환한다.

### 어려웠던 지점

요금 계산 자체보다 "언제 계산하는가"를 잘못 잡은 게 컸다. 출차할 때마다 계산하는 구조로 짜놓으니 기본 요금이 중복으로 붙는 걸 알고도 고치기가 번거로웠다. 그리고 차량번호를 정렬하려고 `int`로 바꿨다가 `"0000"`이나 `"0148"`처럼 앞에 0이 붙은 번호가 `0`, `148`로 변해서 출력 순서가 어긋났다. 마지막으로 올림 처리를 `round`로 해서 `1.5`가 아닌 구간에서 값이 하나씩 모자라게 나온 적도 있었다.

### 해결 방법

"출차 시점에 요금 계산"을 버리고, 기록을 전부 돌면서 시간만 누적한 뒤 마지막에 한 번만 요금을 계산하도록 단계를 분리했다. 누적과 계산을 섞지 않으니 미출차 차량도 "마지막에 23:59로 채워 넣는다"는 한 줄로 끝났다. 차량번호는 네 자리 숫자 문자열로 길이가 고정이라 문자열 정렬이 숫자 정렬과 같다는 걸 확인하고, 변환 없이 `sorted`를 그대로 썼다. 올림은 `math.ceil` 대신 `-(-a // b)` 꼴을 써서 정수 연산으로 처리했다.

### 시간복잡도 / 공간복잡도

* 시간복잡도: O(N log N)
* 공간복잡도: O(N)

`N`은 `records`의 개수(최대 1,000)다. 기록을 한 번 훑는 건 `O(N)`이고, 마지막에 차량번호를 정렬하는 부분이 `O(N log N)`으로 전체를 지배한다.

### 새롭게 알게 된 점

구현 문제에서 "값을 모으는 단계"와 "값을 가공하는 단계"를 섞으면 조건 하나가 추가될 때마다 코드 전체를 손봐야 한다는 걸 알게 됐다. 이번엔 누적만 먼저 끝내고 요금은 나중에 계산하도록 나누자 미출차 처리가 거의 공짜로 붙었다. 그리고 앞자리 0이 의미를 갖는 문자열은 숫자로 바꾸지 않는 게 안전하다는 것도 확실히 기억하게 됐다. 10주차 순위 검색에서 문자열 키를 그대로 딕셔너리에 썼던 것과 같은 감각이다.

## 문제 2

### 문제 정보

* 문제명: 가장 큰 정사각형 찾기
* 문제 링크: https://school.programmers.co.kr/learn/courses/30/lessons/12905
* 사용한 알고리즘 / 자료구조: DP, 2차원 배열

### 처음 접근 방식

모든 칸을 정사각형의 왼쪽 위 꼭짓점으로 보고, 한 변의 길이를 1씩 늘려가며 그 범위가 전부 1인지 확인하는 방식으로 짰다. 변을 늘릴 때마다 내부를 다시 전부 검사하니 보드가 `1000 x 1000`이면 연산량이 감당이 안 됐고 바로 시간초과가 났다. 다음으로는 2차원 누적합을 만들어 임의 사각형의 합을 `O(1)`로 구하고, 변 길이를 이분탐색하는 방법을 생각했다. 될 것 같긴 했는데 누적합 인덱스와 이분탐색 경계를 동시에 맞추다가 계속 틀려서 접근을 바꿨다.

### 풀이 방법

1. `board`의 행 수 `n`, 열 수 `m`을 구한다.
2. `dp[i][j]`를 "`(i, j)`를 오른쪽 아래 꼭짓점으로 하는 정사각형의 최대 한 변 길이"로 정의한다.
3. `board[i][j]`가 0이면 `dp[i][j] = 0`이다.
4. `board[i][j]`가 1이고 `i`나 `j`가 0이면, 더 확장할 공간이 없으므로 `dp[i][j] = 1`이다.
5. 그 외의 경우 `dp[i][j] = min(dp[i-1][j], dp[i][j-1], dp[i-1][j-1]) + 1`로 채운다.
6. 채우면서 최댓값을 기록해두고, 마지막에 `최댓값 * 최댓값`을 넓이로 반환한다.

### 어려웠던 지점

점화식을 왜 `min + 1`로 두는지가 바로 납득되지 않았다. 세 방향 중 하나만 짧아도 정사각형이 깨진다는 걸 머리로는 알겠는데, 왼쪽 위 대각선까지 봐야 하는 이유가 안 잡혔다. 그리고 구현에서는 `i`와 `j`를 1부터 돌리면서 0번 행과 0번 열을 아예 비워뒀더니, 1이 첫 행이나 첫 열에만 있는 보드에서 답이 0으로 나왔다. 보드가 `1 x 1`인 경우도 같은 이유로 틀렸다.

### 해결 방법

작은 보드를 직접 손으로 그려 보면서 세 방향을 모두 봐야 하는 이유를 납득했다. 위와 왼쪽만 길어도 대각선 쪽이 0이면 그 자리는 정사각형의 꼭짓점이 될 수 없으니, 세 값 중 최솟값이 곧 "확장 가능한 한계"였다. 인덱스 문제는 0번 행과 0번 열을 예외로 따로 처리해서 해결했다. 보드를 한 칸 키운 `(n+1) x (m+1)` 크기의 `dp`를 쓰면 이 예외 처리 자체가 없어진다는 것도 나중에 알았다.

### 시간복잡도 / 공간복잡도

* 시간복잡도: O(N * M)
* 공간복잡도: O(N * M)

`N`, `M`은 각각 보드의 행과 열 크기(각각 최대 1,000)다. 모든 칸을 정확히 한 번 채우고, 각 칸에서 보는 값은 이미 계산된 세 개뿐이라 칸마다 상수 시간이다. `board`를 직접 덮어쓰면 추가 공간은 `O(1)`로 줄일 수 있다.

### 새롭게 알게 된 점

2차원 DP에서 상태를 "이 칸을 시작점으로"가 아니라 "이 칸을 끝점으로" 잡으면 이미 계산된 값만 참조하게 되어 점화식이 단순해진다는 걸 알게 됐다. 12주차 스티커 문제에서 선형 DP를 왼쪽에서 오른쪽으로 쌓았던 것과 방향이 같은데, 2차원이 되면 참조할 이전 칸이 세 개로 늘어나는 식이었다. 정사각형처럼 모든 변이 같아야 하는 조건은 `min`으로, 하나만 만족해도 되는 조건은 `max`로 묶인다는 구분도 정리됐다.

## 문제 3

### 문제 정보

* 문제명: 표 편집
* 문제 링크: https://school.programmers.co.kr/learn/courses/30/lessons/81303
* 사용한 알고리즘 / 자료구조: 연결 리스트, 스택

### 처음 접근 방식

행 번호를 담은 리스트를 만들고 명령을 그대로 따라 하기로 했다. `C`는 `list.pop(인덱스)`, `Z`는 복구할 행을 원래 위치에 `insert`, `U X`와 `D X`는 커서 인덱스를 `X`만큼 더하거나 빼는 식이었다. 작은 예제는 통과했지만 `n`이 100만, 명령이 20만 개라 `pop`과 `insert`가 매번 뒤쪽 원소를 전부 밀어서 시간초과가 났다. 그래서 삭제를 실제로 하지 않고 `deleted` 배열로 표시만 해뒀는데, 이번엔 `U X`에서 삭제된 행을 건너뛰며 `X`칸을 올라가야 해서 한 번 이동할 때마다 배열을 훑게 되어 역시 느렸다.

### 풀이 방법

1. 길이 `n`의 `up`, `down` 배열을 만들고 `up[i] = i - 1`, `down[i] = i + 1`로 초기화해 각 행이 위아래 이웃을 직접 가리키게 한다.
2. 현재 커서를 `cur = k`로 두고, 삭제된 행을 쌓을 빈 스택을 준비한다.
3. `U X`는 `X`번 `cur = up[cur]`, `D X`는 `X`번 `cur = down[cur]`를 반복한다. 삭제된 행은 이미 연결에서 빠져 있으므로 자동으로 건너뛰어진다.
4. `C`는 `cur`을 스택에 넣고, `up[cur]`과 `down[cur]`이 서로를 가리키도록 이어 붙여 `cur`을 연결에서 떼어낸다. 그다음 커서는 `down[cur]`로 옮기되, 그 값이 범위를 벗어나면(마지막 행을 지운 경우) `up[cur]`로 옮긴다.
5. `Z`는 스택에서 하나 꺼내고, 그 행의 `up`과 `down`은 지워질 때 값이 그대로 남아 있으므로 양쪽 이웃이 다시 그 행을 가리키게만 되돌린다. 커서는 건드리지 않는다.
6. 모든 명령이 끝나면 길이 `n`의 `"O"` 문자열을 만들고, 스택에 남아 있는 행 번호만 `"X"`로 바꿔 반환한다.

### 어려웠던 지점

"삭제"를 데이터에서 실제로 빼내는 일로 생각한 게 내내 발목을 잡았다. 리스트를 직접 고치면 빠르게 되돌릴 수 없고, 플래그만 세우면 이동할 때마다 훑어야 했다. 복구 명령이 있다는 점도 까다로웠는데, 되돌리려면 "어디에 있었는지"를 기억해야 한다고 생각해서 인덱스까지 같이 저장했다가, 중간에 다른 행이 지워지면 그 인덱스가 전부 틀어졌다. 마지막 행을 지운 뒤 커서를 어디로 보낼지 처리하지 않아서 인덱스 범위를 벗어난 적도 있었다.

### 해결 방법

행을 배열 위의 위치가 아니라 "위아래 이웃을 가리키는 노드"로 보자 두 문제가 한꺼번에 풀렸다. 삭제는 양쪽 이웃이 서로를 가리키게 바꾸는 것뿐이라 상수 시간이고, 지워진 행의 `up`과 `down`은 손대지 않으니 복구할 때 그 값을 그대로 다시 쓰면 된다. 즉 위치를 기억할 필요 없이 이웃 관계만 복원하면 원래 자리로 돌아간다. 복구 순서가 삭제의 역순이어야 하므로 스택이 맞았고, 마지막 행 삭제는 `down`이 범위를 넘는 경우로 따로 걸러 커서를 위로 올렸다.

### 시간복잡도 / 공간복잡도

* 시간복잡도: O(n + m)
* 공간복잡도: O(n)

`n`은 행의 개수(최대 1,000,000), `m`은 명령의 개수(최대 200,000)다. `C`와 `Z`는 포인터 몇 개만 고치므로 상수 시간이고, `U X`와 `D X`는 `X`번 이동하지만 전체 이동량의 합이 명령에 주어진 범위를 넘지 않는다. 마지막에 결과 문자열을 만드는 데 `O(n)`이 든다.

### 새롭게 알게 된 점

삽입과 삭제가 잦고 "되돌리기"가 필요한 문제는 배열 인덱스를 쓰지 않고 연결 관계로 관리하는 게 정석이라는 걸 알게 됐다. 파이썬 리스트가 편해서 `pop`과 `insert`로 해결하려는 습관이 있었는데, 그 두 연산이 `O(N)`이라는 사실이 이렇게 직접적으로 발목을 잡은 건 처음이었다. 또 "역순 복구"라는 요구사항 자체가 스택을 쓰라는 신호라는 점도 챙겼다. 12주차 큰 수 만들기에서 스택을 "불리한 값을 버리는" 데 썼던 것과 달리, 이번엔 "버린 것을 기억해두는" 용도여서 같은 자료구조의 쓰임이 또 하나 늘었다.
